# Accounts, profiles, colours, inbox

Detailed notes, moved out of CLAUDE.md. A `public/js/x.js` path means the source `client/x.ts`; a page's "inline script" is `client/pages/<page>.ts`.

- **User accounts** (required — there is no guest play): a JSON file store at `data/users.json` (gitignored), no database, sized for ~100 users. Passwords are salted `scrypt` hashes; bearer session tokens live in `store.sessions`. REST endpoints: `/api/signup` (email + username ≥4 chars + password ≥4 chars), `/api/login` (username *or* email), `/api/logout`, `/api/me`, `/api/forgot` (email → returns the username), `/api/send-reset` (emails a 30-min reset link — via SMTP when `SMTP_HOST/PORT/USER/PASS/FROM` env vars are set, otherwise the link is logged to the server console and **never returned to the browser**), `/api/reset` (consumes the token, invalidates all the user's sessions). `public/reset.html?token=…` is the reset page. Each user: `id`, `email`, `username`, `color`, `games`, `wordCount`, `currentBadge`, `badges`. Sockets: `create-session`/`join-session` **require** an `auth` token; a writer's name/color come from the account and `creditLine()` (called from `advance()`) adds committed-line word counts (words are counted on `plainText()` — src/sanitize.js, tags gone and entities DECODED, so "shouldn't" is one word; `clip()` cuts `u.lastLine` on a word with an ellipsis), **solo writes count too** (`creditSoloWords(u, doc)`, run from `PUT /api/docs/:id`: credits only what exceeds the document's `creditedWords` high-water mark, so cutting and rewriting never counts twice; a rank-up lands in the inbox), and **every seat shows its words**: `roster()` adds `words` (this story's committed words per account, `gameWords()`) to every writer, friendly or not — the `.chip-words` in the middle of each player pill (the pills are a four-column grid in the side column: `.chip-lead` seat + presence · `.chip-who` avatar + name + the (host) mark · words · `.chip-tail` next/⋯) — and **a non-friendly game keeps score**: the reveal's `#overScore` ranked scoreboard (`scoreboardHtml` in game.html) reads the `scoreboard` on every `game-over` payload (`scoreboard(s)`/`gameOverPayload(s)` in game.js: EVERY account with words in the story, seated or not, so a continued game's earlier contributors and a writer whose seat expired keep their score; `seated` marks who is still at the table; name/colour/avatar from the seat, else the account; `null` for a friendly game); friendly games carry none — appends the game code to `games`, and awards achievements from `lib/achievements.js` (the whole catalogue — names, thresholds, triggers, descriptions — is hand-editable in **`content/achievements.json`**): the word-count ladder (🐶 Puppy Mike 5k → 💛 A Best "Friend" 100k; `currentBadge` = highest tier) and once-per-user word-usage collectibles matched on the stripped text of committed lines (triggers stay secret client-side — `/api/achievements` exposes only the ladder + a usage count). New badges announce in chat; legacy Inkling→Legend ids migrate at startup (`migrateBadges`). Badges ride along on roster entries and chat messages as `badge`. **Public profiles**: `GET /api/users` (auth) lists every account (username/color/badge/wordCount/online — the writers directory on the dashboard, searchable client-side); `GET /api/users/:username` (auth) returns `profileOf()` — the public shape only (never email or account id; `stories` is just a count) — and **a secret badge's recipe never travels on someone else's profile**: `profileOf(u, onlineIds, viewer)` puts a secret usage badge's `desc` into `badgeDescs` only when the viewer has earned that badge too (or is the owner, or an admin — `isSecretUsageId` in store.js), and `usageCaseHtml` shows a worn-but-undescribed badge with a "Secret: they've earned it" teaser; likewise the `badge-earned` toast carries `desc` to the earner's own socket and `desc: null` to the rest of the room for secret badges (`notifyEarned`, the Resume-it-Stupid poke) — plus `hosted`: stories the user is the ORIGINAL host of (code/name/phase/lines + a live `inProgress` flag; profiles show them after About, glowing while in progress; joins are still host-gated so exposing codes is safe). `POST /api/account/profile` saves the About section: plain-text `about` (stripped, ≤500), up to three `links` {label,url} and three `images` urls — **URLs are validated http/https server-side** (rejects javascript:/data:) since they render into other players' DOM; the client still esc()'s everything (`aboutHtml` in profile-view.js). `/profile?user=name` views anyone. **Message a writer**: `POST /api/message {username, text}` (auth, not yourself, ≤1000, the help box's 30s cadence) drops a `note` into their inbox that starts a thread they can Reply into (sender keeps a read `mine` copy); no friendship needed. The profile shows a "✉ Message" button beside the friend button (hidden on your own), opening the `#msgModal` composer. **Avatars ride everywhere**: seats snapshot `avatar`/`avatarFit` (`cover` crop vs `contain` fit — user preference, validated server-side), and roster entries, `game-state` writers, chat messages, and `/api/users` rows all carry them; the client renders them via `miniAvatar()` (util.js) and `avatarHtml()` (profile-view.js), with the initial-letter disc as fallback. **Line editing**: `edit-line {index,text}` lets the author (matched by story-line `userId`) revise their own committed lines during writing/over — sanitized once, `edited: true` flag, re-broadcast. `POST /api/account/email` (password-confirmed) and `/api/account/password` (revokes other sessions) round out settings.

- **Per-user color** is ANY `#rrggbb` — `PALETTE` (`src/sanitize.js` server-side, `public/js/util.js` client-side) is the starter set of swatches, and `/settings` also carries a native `<input type="color">` (`#colorPick`, behind the `.color-pick-ring` well, which wears `.sel` when the colour is off the palette) plus a hex box (`#colorHex`, Enter or leaving the field commits — no Save button; the picker's `change` saves on its own, `input` only paints the ring and the `#colorPreview` username). The server validates the SHAPE (`cleanColor`/`isHex`: six hex digits, lowercased, anything else → a random palette entry) and `safeColor` client-side does the same, so colors are never attacker-controlled when injected into `style=`. Colors tag names in chat, roster, and story bylines.

- **The inbox lives in one module** (`public/js/inbox-panel.js`, `mountInbox({list, unreadChip, readAllBtn, moreLink, limit, replies})`), but the two surfaces are deliberately NOT the same. The dashboard mounts it with `limit: 5, replies: false` — a **notice board**: read it, act on it, delete it, with the ✕ tucked into the row's corner (`.ib-row.ib-compact`) at a size that doesn't compete with the message; no Reply button and no composer markup at all. `public/inbox.html` mounts it whole (`replies` defaults true), and there a message is a **conversation** — one that **folds**: a thread with replies starts collapsed to its opening message plus an `.ib-fold` button naming how many replies are hidden (`foldBtnHtml`; the row's `ib-collapsed` class hides `.ib-chain` and the composer, so the markup never changes and only /inbox ever builds the button). Open threads are remembered in-module across reloads, so answering one doesn't shut it, and folding is not reading (the click doesn't mark the thread read), and its composer is simply THERE — no Reply button to press first: the box sits at the foot of any thread you can answer, addressed to whoever spoke last (Escape clears it, Ctrl/Cmd+Enter sends, no Cancel because there is nothing to close). The delete ✕ is a borderless control in the card's own top-right corner on every inbox surface — a dismissal, not a button competing with the message. Mechanically: `POST /api/inbox/reply` stamps a `threadId` on the reply AND on what it answers (a message with no thread of its own starts one), the sender keeps their own copy (`mine: true`, already read) so both halves show, and `/api/help` mints one thread id across every copy — each admin's and the asker's own — so an answer chains onto the question. `threadInbox()` in dashboard-view.js groups the flat inbox by `threadId` (oldest-first inside, newest exchange first, unread if ANY message is, `replyTo` = the newest message from the other person so a long exchange answers them and not my own last word) and `chainMsgHtml()` renders the follow-ups, sided — mine say "You". Deleting takes the whole conversation; clicking marks all of its unread read.

- **Inbox rows say sender → recipient**: `makeMsg` callers store `toId`, `msgShape(m, owner)` ships `to` (public shape; a received copy resolves to the inbox owner, an old sent copy with no `toId` → null) and `whoHtml(m)` in dashboard-view.js renders `.ib-who` on rows and chain messages ("You" on whichever side is me). **The 20s poll never eats a draft**: `render()` in inbox-panel.js keys rows by `data-thread`, remembers every open composer's text/caret/focus before rebuilding and restores it after.
- **Every inbox ✕ asks first**: `components/confirm-delete.js` (`confirmInboxDelete({conversation, count})`) mounts the site's `.confirm-modal` shape once per page and resolves true/false; `mountInbox` awaits it before any `DELETE /api/inbox/:id` — a lone message and a whole conversation get their own wording. It's a separate module (not in inbox-panel.js) so jsdom can import it; `mountInbox({confirm})` takes a stand-in for tests.
