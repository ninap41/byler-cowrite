# Solo writes: editor, chapters, comments

Detailed notes, moved out of CLAUDE.md. A `public/js/x.js` path means the source `client/x.ts`; a page's "inline script" is `client/pages/<page>.ts`.

- **Solo writes** (`/writes`, `/write`) are the non-game half: one JSON file per document in `data/docs/<id>.json` (`COWRITE_DOC_DIR` relocates it), `src/docs.js` for the store + permissions — **three visibility levels** (`VISIBILITIES` = `private` | `readers` | `public`, anything unrecognised narrows to `private`): `canEdit` = owner only; `canView` = owner, anyone signed in when `public`, or an invited reader when `readers`; `canComment` = owner or invited reader, never a public reader (going public hands out a reader, not a pen). A public write is LISTED — it joins `/api/stories` as `kind: "write"` (games are `kind: "game"`) and opens at `/write?id=`, while `/writes` stays your own shelf plus what you were invited to — **split into two sections** (`docShelfHtml`/`DOC_GROUPS` in write-view.js): "✒️ My solo writes" (yours to edit) and "📖 Beta reading" (someone else's, comment-only). They are different relationships to a document, so they are not one pile sorted by date; each section carries its own count and `.doc-grid`, an empty section isn't drawn at all, and an empty shelf shows one empty state rather than two. The UI is a chip in the editor head naming the current state (`visChipHtml`/`visMenuHtml` in write-view.js — a radio list of three, since three states can't be a toggle), narrowing instantly and confirming only when widening to public; the 👥 Readers button and the 💬 Comment toggle sit beside it as `.head-chip`s — visibility, who can read it, and how you're working in it are one row of state, and the toolbar keeps only formatting (the mode switch is Rich text / HTML), `sanitizeDoc()` for the wider document subset (lists, blockquote, `s`, `a`, `img`, `fs-*` size spans). Inviting a beta reader is a search over the WHOLE writers directory (`inviteOptions`/`inviteRowHtml` in write-view.js): friends sort first and wear a `friend` chip and their row is the invite button; everyone else is a plain `.pick-row.not-friend` div saying "not a friend yet" that carries an **Add friend** button (`POST /api/friends/request` from the picker, the row then reads `requested` — `/api/users` rows carry `requested`) — the server's friends-only rule made visible on the row, with the way past it, instead of an error after the click. The toolbar's 🖼️ (and the chat dock / comments drawer) are on `gradAllEmojis`'s skip list so they render as real emoji, not a gradient outline. The editor page is `public/write.html` + `public/js/write-view.js` (pure string builders) + `components/slash-palette.js` (the "/" reference palette, which also carries the Power Thesaurus link in its footer — it is deliberately NOT a toolbar button). The **HTML view** is pretty-printed one block per line by `formatSource()`; `srcHtml()` (= `unformatSource`) is the ONLY reader of the textarea, so those cosmetic newlines never reach `innerHTML` or the server and can't become `<br>`s.

- **Solo writes are on the profile and the dashboard too**: `GET /api/users/:username` carries `writes` — EVERY document that writer owns, private ones included, as `docSummary` + `mine` + `viewable` (`canView` for the viewer) — and `/api/stories?user=NAME` lists all of that one writer's writes the same way (`docsOwnedBy()` in src/docs.js; the library at large still lists only public ones), each card carrying `viewable`/`visibility`. `soloRowHtml`/`soloListHtml`/`wireSoloDeletes` in write-view.js render them as rows (profile's first column, "Solo writes" card; the dashboard's first column, my own only via `/api/docs`): mine → Continue + a two-click Delete (`DELETE /api/docs/:id`); viewable → Read; otherwise 🔒 Private, listed but not clickable — and on `/stories?user=` a non-viewable write card is `.locked` with no click.

- **Solo writes have CHAPTERS** (`doc.chapters = [{id (12 hex), title, html, wordCount}]`, `src/docs.js`): the chapters are the only source of truth and **`doc.html` is DERIVED** — their html joined with NO marker, recomputed on every read (`ensureChapters` in `readDoc`/`writeDoc`, `syncDocHtml`) and never persisted (`writeDoc` strips it) — so a one-chapter document reads byte-for-byte as the old single blob and every html reader (`countWords`, the anchor helpers, `commentRows`, `creditSoloWords` on the summed `wordCount`, `/api/stories`) is unchanged; a pre-chapter blob on disk migrates to one "Chapter 1" the first time it is read. Comments carry NO chapter field — `chapterOfCid(doc, cid)` finds the chapter whose html holds the anchor, `commentRows` ships it as `chapterId` (null = orphaned), cids stay unique across the whole document (the reuse check runs on the join). `PUT /api/docs/:id {title?, chapters: [{id?, title, html}]}` takes the whole list in its new order (a known id keeps its chapter, an unknown one is minted, each html `sanitizeDoc`'d, each title `cleanChapterTitle`'d — plain, ≤80, "Chapter n" when empty — a chapter left out is deleted and its comments read orphaned; ≤`MAX_CHAPTERS` 200; the legacy `{html}` body still saves a SINGLE-chapter document, 400 otherwise). `docPayload` ships `chapters` beside the joined `html`; `docSummary.chapters` and a `/api/stories` write row's `lines` count them. Sockets: `doc-comment {…, chapterId}` files the comment in that chapter (a single-chapter document accepts none) and **the beta-reader guard runs against THAT chapter's html**; decide/resolve/delete go through `mapChapterHtml`, capturing `chapterOfCid` BEFORE the anchor goes; **`doc-html` pushes ONE chapter** `{id, chapterId, html, chapterWordCount, wordCount}` (no chapter → no push); `doc-updated` carries `chapters`. Client (`write.html`): `chapters`/`openIdx` are the editor's copy, the OPEN chapter lives in the DOM and `stashCurrent()` writes it back into the array before anything reads the list — `allChapters()` is what `save()`, the 30s draft, `beforeunload`, leave-anyway and the exports read, never `currentHtml()` alone; `goChapter()` stashes, swaps the DOM (source view too), resets undo (history is per DOM), clears the composer, re-renders comments (the rail shows the open chapter's, orphans always, heading "N here, M in all", the edge tab the whole story's count) — it never touches the server or `dirty`. The panel `#chapPanel` is the grid's FIRST column (`.doc-main:not(.chap-closed)` = `220px minmax(0,1fr) var(--doc-side-w)`; NOT a second side-drawer, which owns the grid's other variables) toggled by the `#chapChip` head-chip (which always reads "📑 Chapters" — `chapChipLabel()` keeps its signature but where you are is the panel's job, not the chip's; Export and an idle Sprint are icon-only `.head-chip-icon`s with the word in `aria-label`/tip, the save state reads "Saved"/"Unsaved" over a fixed `min-width` so the chips never shift) and by the panel's own ✕ (`.chap-close` in the `.chap-head`, for author and reader alike), remembered as the `chapOpen` editor pref; under 860px it is a fixed dropdown under the head row (`.menu-open`, closed on pick/Escape/outside click/✕) standing on the SOLID `--bg-2`, as does the comments bottom sheet there — a translucent panel over prose is unreadable on a phone. Builders in write-view.js: `chapterListHtml` (author rows ↑ ↓ ✎ ✕ + Add, ✕ disabled on the last chapter, two-click delete; a reader's is the TOC; per-row 💬 counts by `chapterId`), `chapNavHtml` (Prev/Next under the editor, `#chapNav`), `chapChipLabel`, `countWordsHtml`. An unsaved new chapter has `id: null` (no comments can be filed in it until a save — `sendComment` says so). The draft cache (`doc-store.js`) holds the whole chapter list; a pre-chapter `{html}` draft upgrades on read and compares by position. **Export** (`export.js`: `exportChapterHtml`/`exportWork`/`slugOf`, wrapped by `exportDocument`): the `#exportBtn` head-chip's menu offers This chapter / Whole work as a downloaded `.html` for everyone who can open the story, built from the editor's own copy. Tests: `test/docs.test.mjs` (the `chapters:` block), `test/client-write-view.test.mjs`, `test/client-doc-store.test.mjs`, `test/client-views.test.mjs`, `test/pages.test.mjs`.
- **Every sanitizer is IDEMPOTENT, and stored html comes back** (`escapeOnce` in src/sanitize.js: an `&` that already opens one of the five entities the sanitizers write — `&amp; &lt; &gt; &quot; &#39;` — is left alone, and `sanitizeDoc`/`sanitizeAbout` accept their url-bearing tags in the exact form they WRITE them, rel/target and class/alt/loading included). The solo editor sends EVERY chapter on every save and 30s autosave, and the closed ones are the server's own output; a blind second escape grew `'` into `&amp;amp;…#39;` one level per save until the chapter crossed `DOC_MAX` and `slice()` cut its end off (the shrinking word count). So: `sanitizeX(sanitizeX(x)) === sanitizeX(x)` is pinned in `test/sanitize.test.mjs`; `repairEntities()` (src/docs.js, run by `ensureChapters` on every read) collapses an already-mangled `&amp;amp;…#39;` back to its one entity; `PUT /api/docs/:id` REFUSES a chapter over `DOC_MAX` with a 413 instead of cutting it (and a WHOLE story over the 2 MB body limit — every save sends every chapter — gets a worded 413 from the `entity.too.large` handler in `server.js`, not express's html error page; `docs/SAVE_CLEANUP.md` step 6 removes that ceiling); `countWords` counts on `plainText()` (entities decoded, "don't" is one word — the editor's own answer); and `goChapter()` fills the HTML view from the DOM (`cleanHtml`), like `setMode`, never from the stored string. `test/docs.test.mjs` saves the server's own chapters back six times and demands byte-identical html.
- **Find & replace** (`client/components/find-replace.ts`; the toolbar's `#findBtn` and Ctrl/⌘+F open `#findBar`, which lives INSIDE `#docShell` so `--doc-sticky` measures it): pure `findMatches(text, query, {caseSensitive, wholeWord})` (the query is words, never a pattern; no overlaps) over `textIndex(root)` — the editor's text nodes as one string, a block boundary reading as `\n` so a match never spans paragraphs. **A replace edits CHARACTERS in text nodes, never markup** (`replaceInDom`, last match first; a match crossing a tag puts the new word where the old one began), so bold, `fs-*` spans and `cmt` anchors survive and the replacement can never become html; in the HTML view the same bar works on the textarea (`replaceInText`). Scope is the open chapter. Matches are painted with the CSS Custom Highlight API (`::highlight(find-all|find-current)`, no DOM mutation; absent → just the count and the scroll). Replace is the author's alone and off in comment mode (`canReplace`); a reader gets Find. A replace is `onEdit({immediate: true})` — dirty, its own undo step. `finder?.refresh()` re-searches after typing, a chapter switch and a mode switch. Test: `test/client-find-replace.test.mjs`.
- **The solo editor's controls are three MENUS** (the "Editor Toolbar Reorg" design; this supersedes the chip-by-chip head row described below and elsewhere): the head row is Saved · word count · `#sprintLive` (a running sprint's clock, click stops it) · **Share** (`#shareWrap`: the `#visChip` pill rendered into `#visWrap` names the current visibility; the static `#visMenu` holds `#visOpts` = `visOptionsHtml()`, then `#shareBtn` "👥 Beta readers…" with `#readerCount`, then `#commentToggle` "💬 Comment mode" with `#commentState`; a reader gets the Reading pill and no menu) · **Document** (`#docMenuBtn`, which names the open chapter once there is more than one; `#docMenu` holds `#chapChip` "Chapter panel" with `#chapState`, `#promptBtn`, `#sprintBtn`, then the two downloads `#exportChapter`/`#exportWork` — there is no `#exportBtn`). The toolbar row ends in **Aa Appearance** (`#docViewPrefs` > `#viewBtn` + `#viewMenu`: the line stepper, `#fontSelect` = `fontListHtml()` inline radio rows each in its own face (no flip-select), `#paperSelect` = three `data-paper` buttons). `HEAD_MENUS`/`setHeadMenu` in write.ts open one at a time; a pick closes Share/Document, Appearance stays open while you try things; outside click/Escape close. The menus share `.vis-menu`/`.vis-opt` plus `.menu-cap`/`.menu-rule`/`.menu-row`/`.menu-state`, and `.vis-menu` is on `EMOJI_SKIP`. **The body is three flush columns** (desktop, `@media (min-width: 861px)` in base.css): the slab has no bottom margin, `.doc-main` no padding or gap, and the chapter panel and comments card are border-less full-height columns (`top: var(--doc-sticky)`, a single rule where they meet the prose); the phone dropdown/bottom sheet are untouched.
- **The solo editor's head row is ONE SIZE** (`.doc-head-meta :is(.head-chip, .vis-chip, .doc-save-state, #wordCount) { font-size: inherit }` — text and icons alike, nothing bigger than its neighbour; pinned by `test/pages.test.mjs`), in this order: Saved · word count · ⏱ sprint (RIGHT beside the count it measures; a running sprint shows its clock) · the visibility dropdown WITH its words (`🔒 Private ▾`) · 📑 + the OPEN chapter's title (`chapChipLabel(chapters, idx)`, cut at 22ch; tooltip "Chapter 2 of 5") · `⬇ Download` (it says Download) · `👥 Readers` · `🎲 Prompt?` · `💬 Comment` — only the sprint and chapter chips are icon-led; what acts on the story is named in words. The chips have no border and no padding (the row's gap spaces them; hover/`.on` fill in), each icon-only one carries a `data-tip` and an `aria-label`, and `.head-chip, .vis-chip` are on util.ts's `EMOJI_SKIP` list so none wears the gradient outline. **Find is NOT in the head row**: `#findBtn` (`.ghost.tb-find`, the Font Awesome magnifying glass + the word "Find") sits in `#docToolbar` right after Clear formatting; `.toolbar.dimmed .tb-find { pointer-events: auto }` keeps it clickable in the HTML view, and a beta reader (no toolbar) reaches the bar with Ctrl/⌘+F. **Font Awesome on the write page needs its exemption**: `.write-page .write-inner :is(… i …) { font-family: inherit }` is there for italics and outranks `.fa-solid`, so an icon drew as an empty box until the `:is(i.fa-solid, …)` rule right after it gave the icon font back — keep that rule AFTER the inherit one.
- **Prompt? on the solo editor**: the author-only `#promptBtn` head-chip opens `#promptModal`, which mounts the game's own mode picker (`mountPromptModes($("soloPrompt"), {prefix: "soloPm"})`, menus from `/api/prompt-options`) over a Roll button; Roll POSTs `/api/prompt/roll {mode, controls}` (auth; `game.rollPrompt()` — same cleaning, one prompt, nothing stored) and shows the card via `promptHtml`; Insert appears only once something has rolled and drops `promptInsertHtml(prompt)` (write-view.js: ONE `<p class="al-c">`, every `Category: choice` line with the category in `<b>`, lines joined by `<br>` — sanitizeDoc's subset) right after the first h1–h3 or at the top (`insertAfterHeading`), then `onEdit({immediate: true})` so it is dirty and an undo step; Cancel/Escape/backdrop close. - **Sprints** are the solo editor's stopwatch: the ⏱ Sprint head-chip (`#sprintBtn`, author only) remembers the word count when pressed, ticks elapsed time and the delta on the chip, and STOPPING — the button, or leaving the page any way at all (`pagehide`, sent with `fetch(..., {keepalive: true})` so the navigation can't cancel it) — logs `max(0, now − start)` to `POST /api/docs/:id/sprint {words, seconds}` (owner only; clamped). The server stamps it on the account (`u.sprints` newest-first, capped 200, each `{docId, title, words, seconds, at}`, plus `u.sprintWords`) and on the document (`doc.sprintWords`/`doc.sprints`, carried by `docSummary`), so `profileOf` carries `sprintWords`/`sprintCount`, `/api/users/:username` carries the newest 20 `sprints`, and the profile shows a "words sprinted" stat, a Sprints card (`sprintListHtml`/`sprintRowHtml` in write-view.js — each row names and links the project) and "⏱ N sprinted" on solo-write rows. Tests: `test/docs.test.mjs`, `test/client-write-view.test.mjs`.

- **The author's `doc-comment` is version-checked too.** That handler takes the AUTHOR's whole chapter html as it comes (they may have unsaved typing in it; the byte-baseline guard is for readers only) and deliberately doesn't move `rev` — which made a comment the one way to overwrite a chapter without the save route's check: a note left from a tab that was behind rolled the chapter back, and nothing ever flagged it. Now the payload carries `baseRev` (wire.ts) and, for someone who `canEdit`, a `baseRev` that isn't the stored `rev` is refused with `doc-comment-refused {id, cid, reason: "stale"}`; the page drops the pending underline and raises the conflict bar. No `baseRev` = an older client, accepted as before. Same handler: html over `DOC_MAX` is refused (`reason: "long"`) instead of being silently sliced by `sanitizeDoc`, as the save route always did; and the replaced copy goes through `keepBeforeOverwrite`, so a big loss on this path lands in version history. Tests: `test/docs.test.mjs` (stale refused + up-to-date with unsaved typing still lands; over-long refused).
- **Deleting a chapter asks first** (`confirmDialog`, naming the chapter and its word count; an EMPTY chapter just goes). This supersedes the "two-click delete" in the chapters bullet above: the ✕ armed on click one and deleted on click two with no timeout, so a double-click — or a double-tap on a phone's four-button row — removed a chapter in one gesture, undo couldn't reach it (history is per DOM), and the next autosave made it permanent with its comments orphaned. The handler deletes `chapters.indexOf(ch)`, not the index it started with, in case the list moved while the dialog was up. The removed chapter is recoverable after the next save: losing a chapter is a `drop` in version history. Pinned in `test/client-comment-sync.test.mjs`.
- **The save path can't strand words in the page** (2026-09-21, the client half of the lost-words work). (1) **Timeout:** `api(path, body, method, {timeoutMs})` aborts and throws `ApiError` status 0; `save()` passes `SAVE_TIMEOUT_MS` (20s) — a PUT that never answered used to leave `saving = true` forever, after which every save returned `false` at its first line with no message, and (because the idle branch of the tick called `save()`, not `saveDraft()`) the local draft stopped too. (2) **The page may be ahead of the response:** `editSeq` counts every `setDirty(true)`; `save()` remembers it and the chapter OBJECTS it sent (`sent`), and if it moved while the request was out, nothing is replaced, repainted or cleared — the sent chapters only learn the ids the server minted (`sent[i].id = rows[i].id`), the page stays Unsaved, the draft is written. It used to swap `chapters` wholesale and `clearDraft()`, so a chapter added or words typed during a slow save vanished. (3) **The draft is written whenever a confirmed save didn't happen:** every 30s tick FIRST (then the save, if idle and not conflicted), in `save()`'s catch for any failure, on `visibilitychange → hidden` and `pagehide` (`draftIfDirty` — a backgrounded phone tab may never run again), and before the conflict bar's reload. (4) **Drafts are per story** (`cowriteDocDraft:<docId>`, index `cowriteDocDrafts`, newest `MAX_DRAFTS` 6 kept; the old single `cowriteDocDraft` slot is still read, never written) and carry `baseRev`; **`draftIsNewer` no longer compares with `doc.updatedAt`** for a draft that has a `baseRev` — comments, sprints and invites stamp `updatedAt`, so a beta reader's note after a crash used to hide a good draft, and the next save cleared it. A surviving draft that differs is offered, full stop (a confirmed save clears it). **A draft restore takes only the chapters its page edited:** `touched` (a WeakSet of chapter objects, marked in `setDirty(true)`; a full save swaps in new objects, which empties it) rides into the draft as `touched: boolean` per chapter via `draftChapters()` — every `saveDraft` call goes through it, the PUT body never carries the flag. On restore `mergeDraft(draft, doc)` (doc-store.ts, pure) lays the draft OVER THE SERVER'S CHAPTER LIST: the server's chapters in the server's order are the frame; a touched chapter replaces the server's copy (title and html); an untouched one stays exactly as the server has it — so a chapter added, deleted, renamed or rewritten from another tab since survives the restore (before this, the list came from the draft alone: an added chapter was dropped on the next save and a deleted one revived); a never-saved chapter (no id) goes in at its draft index; a touched chapter deleted elsewhere comes back (the writer's words beat the deletion). `draftIsNewer` compares the merged list, so none of those is a difference. A draft with no flags at all restores whole, by position, as it did. Found in the browser: a draft is the whole chapter list, so restoring tab A's draft after tab B had saved chapter two put chapter two's OLD copy back and the next save (now with a current `baseRev`) quietly undid B's work. A draft from before the flag restores whole, as it did. (5) "Restore them" asks first when you've typed since the page opened; `doc-updated` resets the undo history (a Ctrl+Z used to paste the OLD page — possibly another chapter — over the new one) and says when your chapter was removed. (7) **The Save button is disabled** when `!dirty || saving || conflicted` and reads "Saving…" while a request is out (`refreshSaveBtn()`, called from `setDirty`, both ends of `save()` and every `conflicted =`). It was live always, so a click on a clean page re-sent the whole story and moved `rev`, and a double-click's second save returned `false` with no sign. `docs/SAVE_CLEANUP.md` step 2 (drop the button, make the chip clickable) is still open; this is the button telling the truth until then. (6) `cleanHtml` emits `<`/`>` in TEXT nodes as `&lt;`/`&gt;` — raw, `Sarah<Mike…` re-parsed as a tag on the next paint and the words inside were dropped; `&` is deliberately left to the server's `escapeOnce`. Pinned by `test/client-comment-sync.test.mjs` (page wiring), `test/client-doc-store.test.mjs` (the `mergeDraft:` tests, one per case), `test/client-editor.test.mjs`. `docs/SAVE_CLEANUP.md` steps 4 (draft where it helps) and part of 5 are now done; its debounce (1), button (2), leave-flush (3), backoff retry (5) and changed-chapters-only body (6) are still open.
- **Version history** (Document menu → 🕘 Version history…, author only): the copies a story can be taken back to, so an accident is two clicks and not a database restore. WHICH copies are kept is `lib/doc-history.js` (pure, `test/doc-history.test.mjs`) — **spaced by time, never per save**, because autosave fires every 30s and "the last N saves" would all be the damaged copy: `keepReason(entries, prev, next, now)` → `"time"` when ≥`RECENT_GAP_MS` (10 min) since the newest kept copy, `"drop"` when the save loses >`DROP_WORDS` (200) words or a chapter (ALWAYS kept, whatever the spacing — that is what an accident looks like from the server), null otherwise or when the replaced copy was empty; `pruneHistory` keeps the newest `RECENT_KEEP` (12), the last copy of each day for `KEEP_DAYS` (14), and the newest `DROP_KEEP` (10) drop/restore copies. Storing is `src/dochist.js`: one blob per copy in the **cold** kind `dochist` (`storage.cold.get/list/put/del` — async, never loaded at boot, never in memory, not in `KINDS`/`counts()`; files under `data/dochist/`, `COWRITE_HIST_DIR`), named `<docId>_<at>_<reason>_<words>_<chapters>` so a LISTING reads no copies. `PUT /api/docs/:id` snapshots the doc before mutating (`snapshotOf`) and calls `keepBeforeOverwrite()` after `writeDoc` — it never throws (a failed history write must not fail the save). Routes, each `canEdit`-gated (a beta reader gets 403): `GET /api/docs/:id/history` → `{versions: [{at, reason, words, chapters}]}` newest first; `GET …/history/:at` → the copy; `POST …/history/:at/restore` — **a restore is a save**: `rev` moves (an open editor's next save meets the conflict bar), the replaced copy is kept with reason `restore` so it can be undone, html re-sanitized, ids kept. Client: `versionListHtml()` (write-view.ts) rows say when · words · "N more/fewer than now" · why, under a "Now: N words · M chapters" line so the figure every row is measured against is on screen; Download exports that copy through `exportWork`; Restore confirms, puts unsaved words in the local draft, POSTs, reloads. Tests: `test/docs.test.mjs` (`history:` block — drop keeps, restore undoable, chapter removal, author-only), `test/storage.test.mjs` (cold kinds on both backends).
- **The comment-split boot sweep chapters a legacy blob before it drops `html`** (found 2026-09-21, shipped broken in the 09-19 build): `migrateDocComments()` wrote `{...raw, html: undefined}` for every blob still carrying `comments` — and for a story from BEFORE chapters (`html`, no `chapters`; i.e. one nobody had opened since the chapters deploy) `html` was the whole story, so the sweep wrote it out of existence and the next read minted an empty "Chapter 1". It now runs `ensureChapters(raw)` first for a legacy blob (a chaptered one is still written back untouched — a migration is not an edit). Recovery for a story emptied on 09-19 is a database restore point from before that publish. Pinned in `test/storage.test.mjs` (the three older migration tests all seeded chaptered blobs, which is how it got through).
- **Every save names the version it started from** (after a writer lost words, 2026-09-21): `save({quiet, force})` sends `baseRev` on EVERY save — autosave, the Save button, Ctrl/⌘+S, save-and-leave — and the server's 409 raises the conflict bar; the ONLY body without a base is `save({ force: true })` behind that bar's "Save & overwrite". Before this, only the quiet autosave was checked, so a tab that slept through another tab's or device's saves (a reconnect never refetched) could replace newer words with its old copy on one Ctrl+S. `catchUp()` closes the other half: on a socket RE-connect (`connectedOnce`) and on `visibilitychange → visible` it GETs the doc and compares `rev` — a clean tab that is behind reloads onto the newer copy, a dirty one keeps its words and gets the bar. The bar's "Reload to see it" writes the local draft (`saveDraft`) BEFORE it clears `dirty` and reloads, so the reloaded page offers those words back (it used to discard them with no copy anywhere). Pinned by `test/client-comment-sync.test.mjs`. The server still accepts a body with no `baseRev` (`test/docs.test.mjs` "one without a base overwrites") — that is the forced save.
- **Editor view preferences** (`public/js/doc-prefs.js`, localStorage key `cowriteEditorPrefs`) are the writer's own comfort settings and are deliberately NOT document content: they never enter `cleanHtml()`'s output, the saved html, or a beta reader's screen. Three of them, in their own strip (`#docViewPrefs`) BESIDE the formatting toolbar rather than inside it — they are not editing controls, so a beta reader (whose `#docToolbar` is hidden entirely) keeps them; reading someone else's story in the face and spacing you like is exactly what a reader came for: **typeface** (`DOC_FONTS`, menu built by `fontMenuHtml()` which sets each `<option>`'s own `font-family` — and `applyFont()` sets the closed select's too — so the list previews the letterforms instead of just naming them — the families `fonts.json` already loads, so a choice costs no extra download. `--doc-font` is set on the **page root**, not on the two writing surfaces, so the choice dresses the WHOLE write page (title, toolbar, cards, comments): `.write-page .write-inner :is(…) { font-family: inherit }` pulls along everything that hard-codes a face, while the html source view and the size stepper deliberately fall back to mono; `theme` means the theme's own `--font-story`, applied as `--doc-font` on `#docEditor`/`#docSource`), **line spacing** (`LINE_STEPS`, 0.8–2.4, applied as the `--doc-line` CSS var) and **paper colour** (`PAPERS` = `theme` | `light` | `dark`, default `theme` — the `#paperSelect` dropdown next to the line stepper, applied as `data-paper` on `#docEditor`/`#docSource`, styled by `.doc-editor[data-paper=…]` in `base.css`; `theme` sets nothing and keeps the site palette). `DOC_FONTS` is `theme` + the shared registry in `public/js/fonts.js` (loaded families AND system faces), which `test/fonts.test.mjs` pins against `fonts.json`. `savePrefs()` writes the WHOLE blob, so every caller spreads the current prefs in (`savePrefs({ ...prefs, lineHeight })`) or the other preference resets.

- **The write page's sticky furniture** is driven by one measured number: `measureSticky()` writes the live height of `#docShell` (title + toolbar + the unsaved-draft bar, which lives inside the shell) into `--doc-sticky` on a ResizeObserver. The comments pane pins itself at `top: calc(var(--doc-sticky) + 18px)` and is a flex column: `#commentComposer` (the note being written) is pinned and only `#commentPane` scrolls (and `.doc-side { align-self: stretch }` — without it the grid column is only as tall as the card and the sticky child has nowhere to travel), and jumps land clear of the head. Clicking a comment card scrolls to its words and clicking an underline scrolls to its card; the target position comes from `scrollTargetFor()` in write-view.js (pure, unit-tested) rather than `scrollIntoView`, because the head isn't usable space and a smooth scroll that silently no-ops would read as a broken click — a 320ms check lands it outright if the smooth scroll didn't take.

- **Comments are anchored to words, not paragraphs.** A comment pins itself with a marker span living in the document's own html: `<span class="cmt" data-cid="…">the commented words</span>`. `data-cid` is the ONLY data attribute `sanitizeDoc()` lets through and only as exactly 12 hex chars (`CID_RE`/`newCid` in `src/sanitize.js`); `cleanHtml()` must round-trip it untouched or the author's next save would unpin every comment. The underline is that span's CSS, so it travels with the text. `src/docs.js` holds the string surgery — `anchorCids`/`anchorText`/`stripAnchor`/`applySuggestion` (span-nesting aware, no-ops on unbalanced html). **An anchor with no live comment is not a legal state**, and `writeDoc()` enforces it on every write: `pruneAnchors(html, comments)` unwraps any `cmt` span whose cid has no unresolved comment behind it (the words always stay). Without it the author could resolve/delete a comment, hit undo — their history remembers the span, and a dirty editor ignores the server's html push — and save the orphaned marker straight back in, where it showed up in the HTML view. **An anchor is also strictly INLINE** — wrapping a block (`<span class="cmt"><p>…</p></span>`) gives it zero-height line boxes, so the underline draws on nothing and the words look uncommented; `clampToBlock()` clamps a cross-paragraph selection to the block it starts in before it becomes an anchor, and `pruneLocalAnchors()` repairs existing block-wrapping ones (author only — a reader's html must stay byte-identical to the stored copy or their next comment is refused). `pruneLocalAnchors()` in write.html is the editor's mirror of the same rule, run from `renderComments()` (so also after an undo), with a `pendingCids` exemption for an anchor sent but not yet echoed back. **The HTML view is pruned too**: the source textarea is raw text nothing re-renders, so `pruneLocalAnchors()` also runs `pruneSource()` on it, and `decideLocally()` in source mode edits the textarea (`applySuggestionInSource`/`stripAnchorInSource`) rather than the hidden editor — all in `components/comment-sync.ts`, pure (`anchorCids`, `htmlPushKind`, the `*InSource` helpers). A dirty author's refused `doc-html` push paints "New comments arrived…" only when `htmlPushKind()` says an anchor ARRIVED — a delete/reject/resolve is silent, the prune takes the underline. Acting on a card (accept/reject/resolve/delete) drops its cid from `pendingCids` first, so a comment deleted before its echo isn't shielded from the prune forever. **Clicking an underline opens a closed drawer** before focusing the card. `test/client-comment-sync.test.mjs` pins the helpers and the page wiring. Resolving, rejecting and deleting all `stripAnchor()`: the words stay, the underline goes, and a comment with no anchor left reads as `orphaned`.
- **Beta readers can't edit, and that's structural.** `doc-comment` is the one path where a non-owner's action touches the html, and its guard is exact: the client sends the whole html with ONE new anchor, and the server takes it only if the anchor set is exactly the stored one plus the new cid AND `commentBaseline(next) === commentBaseline(ch.html)` (every anchor stripped, split inline runs rejoined — a byte-for-byte echo refused honest comments once a reader's editor re-serialized anything). Any smuggled edit fails that and the whole comment is dropped. That guard applies to READERS ONLY: the author may edit their own document and the editor sends its live html, so requiring a byte match for them silently dropped every comment made after any unsaved typing. A reader's rewrite is stored as `suggestion` and applied only when the AUTHOR emits `doc-comment-decide` (`canEdit`-gated) — accept swaps the words via `applySuggestion`, reject just unwraps. `broadcastDocHtml(doc, socket)` skips the actor, who has already applied it locally (`decideLocally()` in write.html) — necessary because a dirty editor ignores incoming html pushes rather than moving the author's caret.

- **Comments are their own record, and a comment is never an edit.** Reported from production: a beta reader commented while the author was typing and the author got the "changed in another tab — reload" bar, i.e. new comments cost them their unsaved words. Three couplings, three fixes. (1) **Storage:** threads live in `comment/<docId>` (`{docId, comments}`; `data/comments/` on files, `kind='comment'` rows in the one Postgres table — no new table). `readDoc` ATTACHES `doc.comments`, `writeDoc` never persists them (same treatment as derived `doc.html`), `writeComments(doc)` is the only writer; reply/edit/reopen/reply-delete write that record alone, while add/decide/resolve/thread-delete also `writeDoc` for the anchor. Never hand `writeDoc` a doc that didn't come from `readDoc`/`createDoc` — without its attached comments every anchor would be pruned. **Migration:** `migrateDocComments()` runs in `server.js` right after `storage.init()` (and `readDoc` does the same lazily for a blob met later): embedded comments are UNIONED by id into the record — never over it — record written first, then the blob rewritten without them, no `updatedAt` stamp, no prune. Idempotent; pinned against the fake Postgres pool in `test/storage.test.mjs`. After it has run, the PREVIOUS build would show no comments — snapshot the database before deploying. (2) **Version:** the save conflict check is `baseRev` vs `doc.rev`, and `rev` moves ONLY in `PUT /api/docs/:id`. `updatedAt` is still stamped by everything (shelf sort) and is no longer a concurrency token, so comments, `/sprint`, `/readers`, `/visibility` can't refuse an autosave. (3) **Anchor:** a dirty author's editor doesn't take a `doc-html` push (it never did) — and now ignores it for EVERY chapter, not just the open one, since a closed chapter may hold unsaved words too. Instead each comment carries `pos {chapterId, start, text, before, after}` (`anchorPos()` — offsets in the chapter's textContent: tags removed with no space, entities decoded, NOT `plainText`), and on the `doc-comments` push `mergeArrivedAnchors()` calls `placeAnchor()` (`components/comment-sync.ts`): recorded offset if the words are still there, else the occurrence whose surroundings match best, else nothing (the card reads orphaned, as before). It never wraps across blocks, keeps the caret, and runs again on leaving the HTML view. The old "New comments arrived: save to see them" line and `htmlPushKind` are gone. Comments made before this have no `pos` and behave as they did.
- **A comment is a THREAD.** `doc.comments[n]` gains `replies: [{id, userId, text, ts, editedAt?}]`, `editedAt?` and `declined?` — all optional and read defensively (`commentRows` ships `replies: []`, `declined: false`, `edited: false` for a comment stored before threads existed), so threads needed no migration. `commentRows` projects comment and reply through one `voiceOf(doc, userId)` (author/color/avatar/`isAuthor`) so the two can't drift; `userId` never ships for either. Sockets (in `wire.ts` first): `doc-comment-reply {commentId, text}` — `canComment` (author or invited beta reader, **never a public reader**), plain text `stripTags`'d to ≤1000, refused when empty, on a resolved thread (reopen it first) or past `MAX_REPLIES` 50; `doc-comment-edit {commentId, replyId?, text}` — **your own words only**: the document's author may delete a reader's note but never rewrite it, and a suggestion's proposed text is not editable (an empty edit is allowed only on a comment that carries a suggestion); `doc-comment-delete` takes an optional `replyId` (that reply's writer or the document's author; the note survives), without it the whole thread goes as before; `doc-comment-resolve` takes `declined`, honoured only under `canEdit` — **Reject is the author's verdict**, a reader's is stored as a plain resolve, and reopening clears it. None of these touch the html, so none push `doc-html`. The card (`commentHtml`/`replyHtml`/`moreMenuHtml` in write-view.ts): every voice wears a `.dc-tag` pill (`author` | `beta`; a closed note's head shows `.dc-state` — "✓ resolved" / "✕ declined" / "✓ Accepted" / "Not taken" — in its place), the ⋮ (`.dc-more` + `.dc-menu`, drawn only when it would hold something) offers Reopen / Edit / Delete by those same rules — identity is by username, since ids never ship — the closing `.dc-actions` row is bordered buttons (author: Resolve | Reject, or Accept | Reject on a suggestion; a reader: Resolve on their own note), and `.dc-reply` renders only with `canReply` on an open thread. A closed thread folds to one line plus "n replies" (CSS on `.doc-comment.resolved:not(.open)`); a click unfolds it to read (`expanded` in write.ts) instead of jumping to words that no longer wear an underline. **The trap: `renderComments()` rebuilds the rail on every `doc-comments` push, and a push arrives whenever ANYONE replies** — so `snapshotThreadDrafts()`/`restoreThreadDrafts()` lift out every half-typed reply, the open edit box (`editing`) and the caret first and put them back after; anything new that holds typed text in the rail must join that snapshot. Clicks inside `.dc-reply`, `.dc-editbox` and `.dc-menu` must not fall through the pane's click delegate to `focusComment`. Enter sends a reply, Ctrl/⌘+Enter saves an edit, Escape closes the menu or the edit; Delete asks first (`confirmDialog`). `.dc-menu` is `display: grid`, so its `.hidden` twin sits in the grouped block. - **The comments rail is a drawer.** It opens and closes (the ✕ in its head, the `#commentsOpen` edge tab — which carries the comment count so a closed drawer never hides that there are notes) and it resizes: drag `#docSideGrip` (arrow keys work too). Both states are editor prefs (`sideOpen`/`sideWidth`, clamped 240–560 by `clampSide`), and the same number is a column width on desktop (`--doc-side-w` on `.doc-main`) and a bottom-sheet height under 860px, where the rail becomes a fixed sheet. **Selecting text on a phone is how you comment there**, so the composer never renders or steals focus mid-gesture: `touchingText` holds it back until the finger lifts and `coarsePointer()` skips the textarea autofocus that would collapse the selection.

- **The write page is full-bleed**: `<body class="write-page">` drops the top padding, `.write-inner` has no max-width, and the sticky head/toolbar slab runs edge to edge with square corners (as do the editor, the source view and the comments card — mixed radii in a full-width page read as leftovers). Only `.doc-main` carries a gutter, so the prose never touches the bezel.

- **The caret is named on every editing surface** (`caret-color: var(--accent-2)` on `.editor`, `.doc-editor`, `[contenteditable="true"]` and their h1–h3, base.css): the global `h1` is gradient text via `color: transparent`, and a caret is drawn in `color`, so without it the cursor vanished inside a heading in both editors.
- **A heading owns its size.** An `fs-*` span wins on nearest-ancestor, so a 12px span inside an `<h1>` used to render the heading at 12px. Three layers now say otherwise: CSS (`:is(h1,h2,h3) [class*="fs-"] { font-size: inherit }` on every surface — editor, doc read, story, live) makes the heading win whatever arrives by paste or from an older document; `clearSizesInBlocks()` strips the spans out of the DATA when a block format is applied (choosing Heading 2 is choosing a size); and `headingOnly()` disables the size stepper with a tooltip while the selection is inside a heading, so the control is plainly off rather than silently inert.
